# Kotlin 迁移第二批

## 背景

[上一次迁移](2026-11-26-Java-Kotlin增量迁移.md)后，生产代码还剩 30 个 Java 文件。按 `.agents/skills` 中 `java-kotlin-migration-assistant` 和 `kotlin-tooling-java-to-kotlin` 的顺序，先迁移无 Spring 代理和事务风险的叶子类，服务实现、过滤器、Redis Stream 消费和 AI/MCP 留在后面。

## 方案

本批迁移 8 个生产文件，每批先用 `git mv` 单独提交重命名，再提交内容转换，以保留 `git blame`。重命名提交不能单独编译。

| 文件 | 处理方式 |
|---|---|
| `AbstractException` | 同时保留 public 字段（`@JvmField`）和 Lombok 生成的 getter，getter 为 `open` |
| `ClientException`、`ServiceException`、`RemoteException` | 保留全部构造器重载和 `toString` 格式 |
| `Result` | Lombok 的 `@Accessors(chain = true)` 让 setter 返回 `this`，Kotlin 属性的 setter 返回 `Unit`，所以字段保持私有，用显式 getter/setter 保留 JVM 签名，`equals`、`hashCode`、`canEqual` 沿用 Lombok 规则 |
| `Results` | 改为 `object`，静态方法加 `@JvmStatic`，Java 调用写法不变 |
| `ShortCodeUtil` | 改为 `object`，`init` 和 `next` 加 `@JvmStatic`，参数校验顺序和异常消息不变 |
| `LinkUtil` | 保留 `open` 类和构造器注入（测试中被 Mockito mock），静态方法放进 companion 并加 `@JvmStatic` |

其中 `LinkUtil` 为与 Java 完全一致做了两处处理：
- 用 `Character.isWhitespace` 判断空白。Kotlin 的 `isBlank` 会把不间断空格也当空白，Java 不会。
- 复现 `String.split(",")` 去掉末尾空串的行为。

## 影响范围

只改 JVM 源码，没有数据库、配置或部署变更。生产代码剩余 Java 文件从 30 个减到 22 个，测试代码的 17 个 Java 文件未动。

## 测试

- `mvn clean test` 46 个测试全部通过，迁移前后数量相同。
- 用 `javap` 对比迁移前后的 JVM 成员。公开方法、构造器、字段和异常声明一致，差异只有 Kotlin 固有的 `final`、`INSTANCE`、`Companion` 和私有字段改名。
- 差分测试（临时程序，未入库）：把旧 Java 实现改名后与新实现并排运行，同一输入比较返回值或异常的类型与消息。
  - `ShortCodeUtil`：18 项错误路径全部一致。6 位和 7 位、默认和自定义 `a`/`b`、`b` 为负数和超过 N，共 110 万个短码逐个相同，无重复。
  - `LinkUtil`：662 项全部一致，包括 URL 解析、内网地址拦截、IP 头解析、User-Agent 识别、白名单 favicon。

## 遗留问题

- 步长很小（1000）时，`ShortCodeUtil` 的预取线程和主线程会竞争号段，短码序列顺序每次不同。旧 Java 版有同样的竞态，每个短码仍然唯一。默认步长是 10 万，实测无差异。
- `LinkUtil.getActualIp` 遇到只含逗号的请求头（如 `X-Forwarded-For: ,`）会抛 `ArrayIndexOutOfBoundsException`，这是原有行为，迁移时刻意保留。该方法在跳转路径上，需要另行修复。
- 未启动应用做端到端验证，也没有请求 Redis。剩余的服务实现、过滤器、Redis Stream 消费、控制器和 AI/MCP 还是 Java。它们带 `@Transactional`、`@Scheduled`，并被 Mockito 测试 mock，需要先把对应测试迁到 Kotlin，并用 PostgreSQL 和 Redis 容器做端到端验证后再动。
